# CupIT — Prototype Architecture and Implementation Specification

## 1. Project goal

Create a working prototype of **CupIT**, a local-first analytics application for coffee shops.

The prototype must demonstrate the complete architecture and data flow of the future system:

```text
User
  ↓
CupIT Application
  ↓
API / Application Core
  ↓
Data Layer
  ↓
Analytics Engine
  ↓
AI Assistant
  ↓
Results / Recommendations
```

For this prototype, **do NOT implement complicated data parsing**.

Use only structured **JSON files** as the input data source.

The purpose of this version is architectural validation: I want to clearly understand where future CSV, Excel, POS-system, database, or API integrations should be added.

---

# 2. Technology stack

Use:

* Python 3.12+
* Flask for the HTTP/API layer
* JSON for prototype data storage
* Python standard library where possible
* Ollama for local LLM integration
* Docker
* Docker Compose

Do not introduce unnecessary frameworks.

The project should be designed so that individual components can later be moved into separate Docker containers.

---

# 3. Important architectural principle

**Separate data ingestion from business logic and analytics.**

The analytics engine must NEVER directly read JSON files.

Instead:

```text
JSON
 ↓
Data Provider
 ↓
Normalized internal models
 ↓
Analytics Engine
 ↓
API
 ↓
UI / AI
```

Later the JSON provider can be replaced with:

```text
CSV Provider
Excel Provider
PostgreSQL Provider
POS API Provider
1C Provider
Cloud API Provider
```

without changing the analytics engine.

# 6. JSON data provider

Implement:

```text
app/data/interfaces.py
app/data/json_provider.py
```

Create an abstraction such as:

```python
class DataProvider:
    def get_cafe(self):
        ...

    def get_products(self):
        ...

    def get_sales(self):
        ...
```

Then implement:

```python
class JsonDataProvider(DataProvider):
    ...
```

The JSON provider is responsible ONLY for:

* reading JSON
* validating basic structure
* converting JSON into internal Python models

It must NOT calculate analytics.

# 8. Analytics engine

The analytics engine must operate only on normalized Python objects.

It must not know that the data originally came from JSON.

Implement the following analytics.

## Sales analytics

Calculate:

* total revenue
* total number of sold items
* number of transactions
* average transaction value
* sales by day
* sales by category

Example:

```python
calculate_total_revenue(sales, products)
calculate_total_units(sales)
calculate_transaction_count(sales)
calculate_average_transaction_value(sales, products)
```

---

# 9. Product analytics

Calculate:

### Best-selling products

Rank products by:

```text
quantity sold
```

Return something like:

```json
[
    {
        "product": "Cappuccino",
        "units_sold": 153
    }
]
```

### Highest-revenue products

Rank products by:

```text
selling_price × quantity
```

### Lowest-selling products

Find products with the smallest number of sales.

---

# 10. Profitability analytics

For every product calculate:

```text
profit per unit =
selling price - purchase price
```

and:

```text
total profit =
(selling price - purchase price) × quantity sold
```

Rank products by:

* profit per unit
* total profit
* profit margin

Formula:

```text
profit margin =
(selling price - purchase price) / selling price × 100
```

Return structured Python objects/dictionaries.

---

# 11. Daily analytics

Calculate:

* revenue per day

* profit per day

Example:

```json
    "transactions": 48
}
```

# 15. AI endpoint

```text

```

```json
{
```

1. obtain current analytics
2. construct a structured prompt
3. send the prompt to Ollama
4. receive the response
5. return the response as JSON

```json

    "answer": "..."
```

# 16. Ollama configuration

Do not hardcode the Ollama URL.

Use environment variables:

```env
OLLAMA_HOST=http://ollama:11434
OLLAMA_MODEL=<model-name>
```

Create:

```text
.env.example
```

with the required variables.

The application must work without Ollama running.

If Ollama is unavailable:

```text
GET /api/health
```

should still work.

The AI endpoint should return a clear error instead of crashing the application.

# 18. Docker requirements

The Flask application must:

* run inside Docker
* expose its API port
* load configuration from environment variables
* have access to `/data`
* communicate with Ollama through the Docker network

Ollama must:

* run in its own container
* expose port 11434 internally
* have persistent model storage

Use Docker volumes where appropriate.

# 30. Final acceptance criteria

The project is complete only when all of the following work:

1. `docker compose up --build` starts the system.
2. Flask starts successfully.
3. JSON data is loaded through `JsonDataProvider`.
4. The analytics engine calculates real metrics from the sample data.
5. `/api/dashboard` returns correct results.
6. Product rankings work.
7. Profitability calculations work.
8. Daily analytics work.
9. Tests pass.
10. Ollama can be called through `/api/ai/analyze`.
11. The application does not crash when Ollama is unavailable.
12. The analytics engine does not directly depend on JSON.
13. The data layer can theoretically be replaced by another provider without rewriting analytics.
14. README clearly explains the architecture and future extension points.
